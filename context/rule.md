# PayPilot — Development Rules

## What to Use

- Frontend: NextJS, TypeScript, Vite, Tailwind CSS
- Backend: Node.js, Fastify, TypeScript
- Database: PostgreSQL, Drizzle ORM
- AI: DeepSeek with LLM tool/function calling
- Voice: ElevenLabs and Speech-to-Text
- Architecture: Separate frontend, backend, AI agent, tools, and database responsibilities
- Financial actions: Execute only through predefined backend tools
- Validation: Validate all user input and AI-generated tool parameters on the backend

## What to Avoid

- Do not allow the LLM to directly access the database.
- Do not allow the LLM to directly execute SQL queries.
- Do not allow the LLM to directly modify balances, wallets, expenses, or transactions.
- Do not put financial business logic inside prompts.
- Do not trust tool arguments generated by the LLM without backend validation.
- Do not expose database credentials, API keys, or secrets to the frontend or LLM.
- Do not introduce unnecessary libraries or frameworks.
- Do not duplicate functionality already provided by existing project dependencies.
- Do not bypass authentication or authorization for AI-initiated actions.
- Do not allow duplicate financial transactions.
- Do not silently execute sensitive financial actions without appropriate confirmation.

## AI Boundaries

### The AI Can

- Understand natural-language financial requests.
- Interpret text and transcribed voice commands.
- Retrieve financial information through approved tools.
- Decide which tools are required.
- Create multi-step plans.
- Chain multiple tools when necessary.
- Use the result of one tool to determine the next action.
- Explain balances, expenses, debts, and transactions.
- Propose financial actions.
- Request user confirmation before sensitive actions.
- Report the result of completed actions.

### The AI Cannot

- Directly access PostgreSQL.
- Directly execute SQL.
- Directly modify application state.
- Directly modify wallet balances.
- Directly create or modify transactions.
- Bypass authentication or authorization.
- Bypass backend validation.
- Invent transaction results.
- Claim an action succeeded without a successful backend result.
- Decide whether a user has permission to perform an action.
- Override insufficient-funds checks.
- Execute sensitive financial actions without required confirmation.

## Tool Boundaries

Every AI tool must have:

- A clearly defined purpose.
- Explicit input parameters.
- Strict parameter validation.
- Authentication context.
- Authorization checks.
- A predictable response format.
- Clear success and failure states.

### Read Tools

Read tools may retrieve:

- Expenses
- Group information
- Balances
- Wallet balance
- Transaction history
- Debt information

### Action Tools

Action tools may perform:

- Creating expenses
- Adding group members
- Transferring wallet funds
- Settling debts
- Updating financial records

Action tools must always enforce backend validation and authorization.

## Financial Safety Rules

- The backend is the final authority for every financial operation.
- The database is the source of truth.
- Wallet balances must never be updated based solely on an LLM response.
- Every transaction must have a verifiable backend result.
- Failed transactions must never be represented as successful.
- Sensitive actions should require explicit user confirmation.
- Insufficient funds must prevent the transaction.
- Unauthorized users must never access or modify another user's financial data.
- Financial operations must be designed to prevent duplicate execution.

## Architecture Boundary

```text
User
  ↓
Frontend
  ↓
AI Agent
  ↓
Tool Selection
  ↓
Tool Layer
  ↓
Backend Validation
  ↓
Backend Service
  ↓
Database / Wallet
```

The AI controls **reasoning and tool selection**.

The backend controls **permissions, validation, business logic, and execution**.
